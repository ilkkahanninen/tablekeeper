# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Tablekeeper: TTRPG prep and notes stored as a graph (nodes + edges), printed to paper (PDF cards/handouts) for the table. Kotlin 2.1 / JVM 21, Ktor 3 (Netty) + htmx, Pebble templates, Postgres 16 via jOOQ + Flyway, headless Chromium (Playwright) for PDFs. See README.md for the user-facing walkthrough and the module authoring example.

## Commands

```sh
docker compose up --build                 # app + Postgres, http://localhost:8080
docker compose up -d db                   # just Postgres, published on 127.0.0.1:5432 (the app's default DATABASE_URL)
./gradlew run                             # app on the host (IntelliJ: shared "Tablekeeper" run config in .run/); stop the app container first, both use :8080
./gradlew test                            # unit tests (no database)
./gradlew smokeTest                       # the whole app against Postgres in Docker (Testcontainers); needs Docker running
./gradlew check                           # both
./gradlew test --tests 'tablekeeper.modules.GameModulesTest'                       # one class
./gradlew test --tests 'tablekeeper.modules.GameModulesTest.landmark is a place*'  # one test (backtick names, use a wildcard)
```

CI (`.github/workflows/ci.yml`, on pushes and PRs to `main`): `./gradlew check` (with `CI` set, `installChromium` also apt-installs Chromium's libraries), then on pushes the image is built natively for amd64 and arm64, pushed to `ghcr.io/ilkkahanninen/tablekeeper` and tagged as one multi-arch image, then `deploy` POSTs to the `DEPLOY_WEBHOOK_URL` secret, signed with `DEPLOY_WEBHOOK_SECRET` (skipped while unset).

Tests load the real `./modules` directory (passed as the `modulesDir` system property in `build.gradle.kts`) and need no database. Smoke tests (`src/smokeTest`, `Smoke.kt`) run the real `Application.app` (`App.kt`) in-process against a throwaway Postgres 16 container, so routes, SQL and templates are checked too. The `X-Smoke-User` header picks the user (default `alice`), and every test makes its own campaigns. Add one for a new route or query, and an ownership check (`OwnershipSmokeTest`) for anything that takes an id. Under docker compose, `./modules` is mounted and `TEMPLATE_CACHE=false`, so print templates reload live; `module.json` changes need an app restart.

## UI rules

- Cut taglines, helper text and secondary labels (subtitles, "No X yet." messages, placeholders, type labels next to codes). If a screen needs them to make sense, fix the layout instead: table headers, grouping, ordering.
- On screen a node is shown by its type icon (`node/_icon.peb`, needs `module` in the model; tip "Landmark L1"), never by its code; dropdown options show just the name. Prints keep codes. New icons: copy the Lucide SVG body into `static/icons.svg` and add the name to `ICONS`.
- Two button levels, one size (`static/app.css`): primary (a plain `<button>`, or `.primary` on a menu's summary) only for the action that completes a small form you just filled in (Add, Create) and the top bar's Create ▾; `class="secondary"` for everything else. `×` icons (`.unlink`) and dropdown rows (`.menu` / `.menu-item`) aren't buttons. No per-feature button styles.
- Make the decision that improves UX, DX and AX together, without breaking anything. Prefer module data and shared partials over one-off markup.
- Node pages autosave: `_form.peb` posts on `change` with `autosave=1`, and only `#save-status` is swapped. Never swap the form there, or focus and typed text are lost. The title is first on the page in its own form (`node/_title.peb`, posting `only=` so nothing else changes); the main form doesn't post a title, and the save keeps the stored one.

## Architecture

**Game modules are data, not code.** `modules/<id>/module.json` declares node types, edge types and props JSON Schemas; `GameModules.load` (`modules/GameModules.kt`) resolves each module's `extends` chain (base first, self last) into a `ResolvedModule` (`modules/ResolvedModule.kt`, the queries everything else uses). The JSON shape is in `modules/ModuleDef.kt`; `modules/ModuleChecks.kt` validates every setting at startup, so add a check there with each new setting. At load, `props` are expanded (`modules/Props.kt`: the short form is wrapped as a closed object schema, `"@name"` / `{"use": name}` take the module's shared `fields`), then `patchTypes` and `extends` are resolved once with one rule (`modules/Overlay.kt`: objects merge key by key, lists, values and `props` replace; `id`, `label`, `plural`, `codePrefix` aren't inherited), so `ResolvedModule` reads each type's settings directly. Grouped settings: `overview {columns, sort, muted, hidden}`, `print {template, summary, nested}`, `campaignMap {shape, depth, between}`; old flat keys fail load with a hint. Key behaviours that span the app:
- Node types inherit via `extends` (`heart.landmark` → `core.place`). `isA` walks this chain and is used everywhere instead of type equality: link rules and fact detection (`isA(type, "core.fact")`).
- `hide` removes inherited types from "New…" menus only; they still resolve.
- Edge types define `from`/`to` type lists plus `label`/`inverseLabel`. `linkOptions` exposes each edge in both directions (OUT uses `label`, IN uses `inverseLabel`), so "located_at" on a landmark appears as "has here".
- Props schemas drive both validation (networknt, draft 7) and form generation (`PropsForm.kt`; widget mapping is in README).

Prefer adding game-specific behaviour to module JSON/templates over adding Kotlin special cases. Dice-rated props store the die itself (`d4`…`d12`) as the enum value; any name for a die (e.g. "Professional") goes in `x-enumLabels` ("d8 Professional").

**Storage** (`db/migration/V1__init.sql`): a generic graph. `nodes` hold `type`, a per-campaign short `code` (prefix from the node type + next number, allocated under a Postgres advisory lock in `GraphService.createNode`), `props` JSONB and `visibility` (`gm`/`players`/`revealed`); `edges` link nodes with a `type` string. jOOQ is used only as a plain-SQL executor (no codegen); queries are hand-written strings in `CampaignService`/`GraphService`. Schema changes go in new Flyway files `V<n>__*.sql`, run automatically at startup.

**Export files** (`core/CampaignTransfer.kt`) carry a format `version`. Old files are upgraded on import by `core/ExportUpgrades.kt`, one frozen step per version, each doing to the file what that version's Flyway data migrations did to stored data. A migration that rewrites node, edge or table data (or a change to the export shape) raises `CampaignExport.VERSION`, adds its step, and saves an export made by the new version as `src/test/resources/exports/v<version>-<module>.json`. Never edit older fixtures. `ExportCompatibilityTest` imports every fixture and checks its props against the module, and it fails on any new migration until its `checkedMigration` is raised.

**Ownership scoping:** every campaign has an `owner_id`; every graph query takes a `campaignId` that the caller must first resolve via `CampaignService.get(user, id)` (see `call.game()` in `web/Routes.kt`, which also gives the campaign's module). Keep this invariant for new queries. `AUTH_MODE=none` resolves every request to a single `local` user (`auth/Auth.kt`). `AUTH_MODE=session` resolves the session cookie (`SessionUserResolver`, `auth/Accounts.kt`: Argon2id passwords in `auth/Passwords.kt`, sessions as SHA-256 of a random token in `sessions`, 30 days, extended in their second half); no user means `call.user` throws `NotAuthenticated`, which `StatusPages` turns into a redirect to `/login?next=…` (HX-Redirect for htmx, 401 for the rest). Sign-up is open; `local` (no password) can't log in, so its campaigns stay with `none` mode. Login routes (`web/AuthRoutes.kt`) exist only in `session` mode; `call.html()` gives every page `me` for the top bar's user menu; failed logins are throttled per name and address (`LoginThrottle`). In both modes the CSRF plugin (`App.kt`) refuses a POST whose `Origin` isn't the app's (Host, or `PUBLIC_URL` behind a proxy), so a scripted POST (curl, tests) must send `Origin` and `Host`.

**Print pipeline** (`print/PrintService.kt`): `model()` builds the template model and does all audience filtering (`core/Audience.kt`) *before* any template runs, so a template can't leak GM-only nodes onto a player handout. Visibility and player handouts are intentionally hidden from the UI for now (no form field, no handout link) but kept in the data model and backend; the save route keeps the stored visibility when none is posted. Linked fact nodes are split out into `facts`; other links are grouped by their directional edge label. The template is the type's `print.template`, else `print/session.peb` for a type with a `packet`, else `print/generic.peb`; every print draws a node with `print/_body.peb` (props, linked props, notes, long texts as their own sections, links, facts, the node's own map), so a module needs no print templates. HTML becomes PDF in headless Chromium (`print/Chromium.kt`, behind `HtmlToPdf`): one thread owns the browser (Playwright objects are single-threaded), a page has scripts off and gets nothing from the network but the app's fonts, and the page size is the template's `@page`. Every print template includes `print/_fonts.peb`: embedded Alegreya (text), Alegreya Sans (codes, map labels) and Noto Sans Symbols 2 (fallback), from classpath `fonts/` (also served at `/fonts` for the print preview; sources and licences in `fonts/SOURCES.txt`). Chromium kerns and sets ligatures; keep the fonts static (a variable font embeds as Type 3). `./gradlew installChromium` installs the browser (`run` and `smokeTest` depend on it; the Dockerfile installs it too). The Docker image is slimmed in the `Dockerfile`: a `jlink` runtime with a listed set of JDK modules (a new dependency may need one added: it shows as `NoClassDefFoundError` for a `java.*`/`jdk.*` class), Playwright's driver jar cut to the image's platform, and Chromium's fallback fonts and Mesa/LLVM removed (a build-time PDF check guards that). Tests don't use the image: after changing it, run it against the compose database and print a packet.

**Map** (`map/`): `MapService.view` builds the campaign map from module `campaignMap` settings (linked above the campaign page's title, not in the top bar); `MapService.nodeView` builds a node's own map from its type's `map` setting (a MÖRK BORG dungeon's rooms, cropped to them; linked next to Print on its page, and `nodeMap` in its print model). `MapLayout` is a deterministic, server-side force layout. It runs on the server so the same SVG (`templates/map/_svg.peb`) serves the screen page and the PDF.

**Session packet** (`PrintService.packet`, `print/Packet.kt`): print models are typed (`PrintModel`, passed to templates via `asMap()`); when a node's type has a module `packet` setting (Heart: `core.session`), its print model also gets `map`, `views` (built by `views/ModuleViews.kt`, the same code as the `/v/{view}` pages) and `sections` (print models of the selected nodes and the `between` ones). Selection is the session's `checklists` (links via `features`); `around` (NPCs, factions) is anchored to the selected and the `between` nodes. `PrintService.packet` then leaves out `packet.leaveOut` nodes (dead NPCs; the debrief keeps them) and other sessions from entries and lists; the cover's "To reveal" is the session's own facts (`plans_reveal`), and `packet.soFar` lists a type's nodes up to this session (MÖRK BORG's miseries). Props a type's `displayTitle` shows aren't print rows. The packet template is the shared `print/session.peb` (cover, then each view's `print` partial, e.g. `heart/print/_inspiration_packet.peb`, then sections drawn with `_body.peb`). Multi-column text (`packet.columns`) is done by imposition (`print/Imposition.kt`): the template's `columns` part is rendered once per section (variable `only`, the template then leaves out that section's h2) as one column on narrow pages, and PDFBox places those pages side by side on landscape sheets, each section from a new column, under a page of `print/sheets.peb` (also rendered by Chromium) with every section's heading in a band across its columns and the sheet's number (so a continued section is headed again). CSS columns can't repeat a continued section's heading, so keep the imposition.

**Debrief** (module `debrief`, `web/Debrief.kt`, `NodePage.debrief`, `node/_debrief.peb`): a session page lists its packet's nodes (`Packet.select`, the same selection as the print) with some fields, link slots and linked nodes editable in place. Every control posts to the *other* node's existing routes: a node save with `only=<field>` (repeatable) merges just those props over the stored ones (`PropsForm.parse`'s `only`/`stored`), `clear=1` empties them (Done); slot and quick-create posts take `quiet=1`, which answers with nothing instead of swapping the session page's parts with the other node's. `refresh=1` sends the `debrief-changed` event that reloads the section from `/n/{id}/debrief`.

**Notes** (`core/Notes.kt`): a node's `body` and its long-text props ("textarea", "list") are stored as typed and rendered by `Notes.html` (`Notes.inline` for fact text and print summaries) into escaped HTML with paragraphs, `- ` lists, `**bold**`, `*italic*` and `[[mentions]]`, which `Mentions` resolves by code, title or display title (any case). Templates print it with `| raw` (`notes` and `fieldViews` in the node page model, `notes`, `PropLine.html`/`items` and summaries in print models), so never put user text in there unescaped. Mentions aren't edges: "Mentioned in" is a query (`GraphService.mentioning`), and a rename rewrites `[[old]]` in all notes (`renameMentions`). On the page, every long text uses `node/_long_text.peb` (formatted view, then a textarea on click); its `#view-<key>` is swapped out-of-band after a full-form autosave; the edit toggle and the `[[` picker (`/n/{id}/mentions`) are in `static/app.js`.

**Random tables** (`core/RandomTableService.kt`, migration V3) are campaign data the user types; a module's `tables` are only starters, seeded into its new campaigns (`RandomTableService.seed`, and the Tables page's "Add the game's tables"). Fields are keyed `"<type id>:<field>"` (`title` or a prop name); a field can have several tables (`node/_random.peb` then shows a menu). All rolls happen on the server in `RandomTables.roll`: new node titles (`Deps.newTitle` in `web/Routes.kt`) and the Random buttons, which fetch `/tables/{id}/roll`. `static/app.js` then fills the field and fires `change`, so autosave stores it. Don't duplicate the roll logic in JS.

**Generators** (`generate/`): a module's `generators` make a set of linked nodes in one click (Create ▾ → `POST /c/{id}/generate/{gid}`). `Generator.plan` decides everything up front and is pure (a `Rolls` passed in, seeded `Random` in tests); a group can take several fields from one `|`-separated table `row` (MÖRK BORG's Bestiary, by table name), or be made by another `generator` (its plan appended, its first node the member; cycles fail module load). `GenerateService` rolls on the campaign's tables (same `RandomTables.roll`) and stores the plan through `GraphService` and `Linker`. Built-in `connect` layouts (`DungeonLayout`) are listed in `GEN_LAYOUTS`. A module's `starter` (not inherited) is a generator run once when a campaign is created, after its tables are seeded (`POST /campaigns`); imports get neither. Links on pages and prints are sorted by type, then code in number order (`codeOrder`: R2 before R10).

**Templates** (`templates/Templates.kt`): one Pebble engine (auto-escaping on) for screen and print. Names resolve against the classpath (`src/main/resources/templates/`) first, then the modules directory, so module templates are referenced like `heart/views/inspiration.peb`. Screen UI is server-rendered with htmx partials (`templates/node/_*.peb`); htmx is vendored in `static/`.

**Wiring:** `App.kt` builds everything by hand (no DI) and passes a `Deps` bag to `Application.routes`. `Deps` also holds the request helpers (`call.game()`, `call.html()`, `call.redirect()`, `call.linksChanged()`), and the route files (`web/CampaignRoutes.kt`, `NodeRoutes.kt`, `TableRoutes.kt`) run inside `with(d)` so they read as plain calls. Keep handlers thin: node-page view models are in `web/NodePage.kt`, link rules (`linkLimits`, slot replacement) in `modules/Linker.kt`, campaign-home tables in `web/Overview.kt`. Domain errors (`core/Errors.kt`: `NotFound`, `BadRequest`, `HiddenFromAudience`; plus `auth`'s `NotAuthenticated`) are exceptions mapped to HTTP status in `StatusPages`.

**Package layers:** `core` (graph, campaigns, random tables; depends on nothing else here) ← `modules` ← `views` / `map` / `print` / `templates` ← `web` ← `App`. Pages and prints that walk the whole graph load it once with `GraphService.snapshot()` (`core/CampaignGraph`, pure) and follow links with `linkedNodes`; a node's `context` parent is `ResolvedModule.parent(graph, node)`.

## Known gaps

From README: no password reset (an admin sets a new hash), player handouts (hidden from the UI). Smoke tests check that routes answer and pages and PDFs render, not how they look: check layout changes by running the app against a throwaway campaign (e.g. `PORT=8099 ./gradlew run`) and deleting it afterwards.
